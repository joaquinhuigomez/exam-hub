2. Master mental framework

Every AWS ML/data question maps onto this pipeline. When stuck, ask "where in this pipeline am I?"

INGEST → STORE → TRANSFORM → TRAIN/PROCESS → SERVE/OPERATE → SECURE/GOVERN (cross-cutting)

For answer selection, apply AWS's own bias, in priority order:

  1. Managed > self-managed (SageMaker built-in > custom container; Glue > self-hosted Spark on EC2)
  2. Serverless > provisioned when traffic is unpredictable (Serverless Inference, Redshift Serverless, Aurora Serverless)
  3. Least privilege always wins security questions — narrower IAM/VPC scope is correct
  4. Cost-scored questions: Spot > On-Demand for training; Savings Plans > Spot for steady-state inference
  5. "With minimal operational overhead" → pick the managed/serverless service

This single framework resolves ~40% of scenario questions on both exams without needing deep service knowledge.

3.2 SageMaker Studio — what's new in 2026

SageMaker Unified Studio is the strategic direction: merges SageMaker, Redshift, Glue, Athena, EMR, and Bedrock into one workspace with a shared project/permissions model (built on Amazon DataZone) — the link between the ML and Data Engineering certs. As of May 2026, it added guided getting-started tutorials and in-product release notes.

Studio Classic is legacy, being sunset in favor of Unified Studio. Assume Unified Studio unless a question is explicitly about legacy migration.

Exam angle: "collaborate in one governed workspace with row/column-level permissions" → SageMaker Unified Studio + Lake Formation permissions, not shared admin IAM.

3.3 Training — core concepts + worked example

Built-in vs Script Mode vs BYOC: Built-in (XGBoost, Linear Learner, k-means) wins on "least development effort" questions when the algorithm fits. Script Mode = your train.py in a managed framework container (PyTorch/TensorFlow/HuggingFace). BYOC = full custom Docker image — only when the framework/runtime isn't supported at all.

Worked example: "Fine-tune a HuggingFace transformer with custom loss logic on a single GPU, minimize infra work." → Script Mode with the HuggingFace DLC. Not built-in (no built-in covers custom transformers/loss). Not BYOC (HF has a managed container already).

Distributed training — the two axes

  • Data parallelism: same model copied across devices, each sees a data shard, gradients synced (all-reduce). Use when the model fits on one device but you want speed/bigger batch. SageMaker's smdistributed.dataparallel (SMDDP), optimized for EFA network topology.
  • Model parallelism: model too big for one device, split layers/tensors across devices. smdistributed.modelparallel (SMP) — pipeline parallelism (split by layer) or tensor parallelism (split within a layer, for huge LLMs).
Hook: "Data parallel = same model, split data. Model parallel = same data, split model." "Doesn't fit in GPU memory" → model parallel. "Too slow / want bigger batch" → data parallel.

Training Compiler: auto-optimizes DL training code at the graph/kernel level — pick for "reduce training time/cost, no code changes."
Managed Spot Training: up to 90% savings, auto checkpoint/resume on interruption — trigger phrase: "minimize cost" + "can tolerate interruptions."

3.4 HPC / HyperPod — the deep dive

SageMaker HyperPod = persistent, purpose-built compute clusters for large-scale distributed training and (increasingly, 2026) inference — AWS's answer to training/serving foundation models across hundreds of GPUs without hand-managing infrastructure.

  • Resiliency: auto-detects faulty nodes, replaces them, resumes from last checkpoint — the #1 exam differentiator vs rolling your own EC2/Slurm cluster. Trigger: "training on 100s of GPUs keeps failing due to hardware faults, minimize manual intervention" → HyperPod.
  • Orchestration choice: Slurm or Amazon EKS — pick by team familiarity, same resiliency either way.
  • Task governance: prioritize/pause/resume training tasks across teams sharing a cluster (multi-tenant GPU quotas).
  • Restricted Instance Groups (RIG): isolate instance groups for compliance-sensitive workloads within a shared cluster — got comprehensive observability in March 2026.
  • 2026 additions: enhanced Ray support (create/manage Ray clusters from Studio's web UI, attach JupyterLab/Code Editor for interactive cluster-scale iteration); new instance support incl. G7e (NVIDIA RTX PRO 6000 Blackwell, up to 2.3x better inference perf than G6e, up to 768GB total GPU memory) and r5d.16xlarge; Disaggregated Prefill and Decode (DPD) — separates LLM inference's prefill phase (compute-bound) from decode phase (memory-bandwidth-bound) onto dedicated GPU pools. This is new-generation content, more likely tested in MLA-C02 than the retiring C01.
When does the exam want HyperPod vs plain Training Jobs? Plain job = single run, no persistent cluster needed. HyperPod = persistent, shared, multi-team cluster for repeated large-scale (often foundation-model) training/inference with automatic fault recovery. Triggers: "hundreds of accelerators," "foundation model," "cluster shared across teams," "automatic node replacement."

Sources: HyperPod features · Ray support · DPD · RIG observability · G7e/r5d instances

3.5 Hyperparameter tuning — Automatic Model Tuning (AMT)

StrategyHow it worksPick when...
Grid SearchExhaustive, every combinationSmall, discrete space; guaranteed full coverage
Random SearchRandom samplingLarge space, cheap per-trial baseline, trivially parallel
Bayesian (default)Regression over past trial results to pick next comboModerate budget, best result per training dollar — AWS's preferred default
HyperbandMulti-fidelity — small budgets first, kill underperformers early, reallocateLarge number of candidates + want speed — up to 3x faster than Bayesian
Hook: "Grid = exhaustive & slow. Random = cheap & dumb. Bayesian = smart & sequential. Hyperband = smart & parallel-with-early-stopping." Question emphasizes time/speed + many candidates → Hyperband, not Bayesian.

Other AMT facts: Warm start reuses a prior tuning job's results as a prior for a new one. Up to 750 total training jobs per tuning job. Multi-algorithm HPO tunes across several algorithms in one job.

Source: SageMaker AMT how it works

OptionLatencyTraffic patternCost model
Real-time endpointmsSteady, predictable, always warmPay for provisioned instance 24/7
Serverless Inferencems–low-sec (cold start)Intermittent/unpredictablePay per inference + duration, scales to zero
Async Inferencesec–minLarge payloads (>1MB) / long processingPay for instance only while processing queue
Batch TransformofflineEntire dataset upfront, no live requestsPay only for job duration
Multi-Model EndpointmsMany similar-sized models, sparse trafficBig cost saver — dynamic load/unload from S3

Trigger-phrase mapping (high-yield, memorize): "unpredictable/intermittent, cost-sensitive, can tolerate short delay" → Serverless. "Large payload, long-running, no immediate response needed" → Async. "Have all the data already" → Batch Transform. "Hundreds of small models, low per-model traffic" → Multi-Model Endpoint. "Always-on, latency-critical, predictable" → Real-time (+ consider Savings Plans).

Also know: Inference Recommender (auto-benchmarks instance types/configs — "which instance type should I use" → this, not manual trial and error) and SageMaker Neo (compiles models for target hardware, edge or cloud — "deploy to edge" or "reduce latency without changing accuracy" → Neo).

3.7 MLOps layer

Pipelines: native CI/CD-for-ML DAG (processing → training → eval → register → deploy). Model Registry: versioned catalog with approval workflow (Pending/Approved/Rejected) gating production promotion. Model Monitor: detects data/model-quality/bias/feature-attribution drift against a baseline. Projects: pre-built MLOps CI/CD templates (CodePipeline/CodeBuild).

Worked example: "Prediction quality degrading in prod, want automatic alerting when input distribution shifts." → Model Monitor with a data-quality baseline + CloudWatch alarm on the monitoring schedule's violation metric.

3.8 Security (Domain 4)

  • Training/inference in a VPC with no internet → VpcConfig + VPC endpoints (PrivateLink) for S3/ECR access.
  • Network isolation mode (EnableNetworkIsolation=True): container can't make any outbound calls — strictest option for untrusted code / compliance.
  • Encrypt everything with KMS: EBS volumes, S3, inter-container traffic (InterContainerTrafficEncryption).
  • IAM: SageMaker execution role scoped per-project/team — never one shared admin role across notebooks.

4. Data Engineering Associate — the non-SageMaker half

You already have real-world muscle memory with Lambda/Athena/Redshift/Glue/S3 at Amazon — the exam gap is usually edge-case service selection and governance, not fundamentals.

4.1 Ingestion & Transformation (34% — center of gravity)

Batch: Glue (Spark, serverless, visual + code), Glue DataBrew (no-code prep), EMR (need full Spark/Hadoop control or existing jobs), Step Functions (multi-service orchestration).

Streaming: Kinesis Data Streams (custom consumers, fine control) vs Kinesis Data Firehose (fully managed delivery to S3/Redshift/OpenSearch, no consumer code) vs MSK (need Kafka compatibility/tooling).

Hook: "Streams = you write the consumer. Firehose = AWS writes the consumer." "No code, deliver straight to S3" → Firehose.

Glue specifics to know cold: crawlers (auto-discover schema → Data Catalog), Glue Data Quality (DQDL declarative rules), Glue Studio (visual ETL), job bookmarks (incremental processing).

4.2 Data Store Management (26%)

S3 (data lake, cheap, decoupled) · Redshift (data warehouse, complex analytical SQL at scale) · DynamoDB (low-latency KV/NoSQL) · RDS/Aurora (transactional, relational) · OpenSearch (search/log analytics).

Redshift Spectrum: query S3 directly from Redshift without loading — "query data lake + warehouse together." Redshift Serverless: unpredictable analytics workloads, same serverless-when-unpredictable rule as SageMaker. Lake Formation: governance layer on S3-based lakes — fine-grained (row/column/tag-based) permissions across Glue/Athena/Redshift Spectrum/EMR.

4.3 Data Operations & Support (22%)

Orchestration: Step Functions (service-to-service) vs MWAA (complex DAGs, existing Airflow) vs Glue workflows (Glue-native, simpler). Monitoring: CloudWatch (metrics/logs/alarms), CloudTrail (API audit), job-specific logs (Glue/EMR).

4.4 Data Security & Governance (18%)

Lake Formation permissions is the single most-tested concept here. KMS encryption everywhere, IAM least privilege, Macie (PII discovery/classification in S3). Governance = who can see what, lineage, cataloging (Glue Data Catalog is the shared metadata store across Athena/Redshift Spectrum/EMR/Glue).

5. Cross-cutting memorization tricks

  1. "Managed-first" reflex: when two services could work, AWS's own answer is the more managed one. Kills most wrong-answer distractors.
  2. Cost-trigger words: "minimize cost," "intermittent," "unpredictable" → Serverless/Spot/scale-to-zero.
  3. Latency-trigger words: "real-time," "sub-second," "immediate" → real-time endpoint / DynamoDB / Kinesis Streams, never batch.
  4. "Least operational overhead" = AWS-speak for "pick the fully managed service," full stop.
  5. Build a flashcard deck of trigger-phrase → service pairs from sections 3.6 and 4.1 — those two tables alone likely cover 15–20% of total scored questions across both exams.
  6. For HPO strategies (3.5) and Inference options (3.6): rehearse the tables out loud until you can regenerate them from memory — highest-yield "matching" question types.

7. Hands-on exercises — do these in your own AWS account

Ordered ~100→400 difficulty; each maps to a specific exam domain so you drill and build portfolio evidence simultaneously.

  1. (100) Data prep + built-in algorithm: Load a small tabular dataset to S3 → SageMaker Studio (Unified) → Data Wrangler flow to clean/transform → train an XGBoost built-in model. (MLA D1/D2)
  2. (150) Script mode training: Same dataset, write a simple PyTorch/scikit-learn train.py, run via Script Mode. Compare setup effort and cost vs #1. (MLA D2)
  3. (200) Hyperparameter tuning: Wrap #2's job in an AMT tuning job — once Bayesian, once Hyperband. Compare wall-clock time and best objective metric. (MLA D2 — tests §3.5)
  4. (200) Inference option comparison: Deploy the trained model three ways — real-time endpoint, Serverless Inference, Batch Transform against a static file. Compare cost/latency directly. (MLA D3 — tests §3.6)
  5. (250) MLOps pipeline: Build a SageMaker Pipeline chaining processing → train → evaluate → conditionally register in Model Registry only if accuracy exceeds a threshold. (MLA D3)
  6. (250) Model Monitor: Baseline your endpoint's inputs, feed it deliberately skewed data, watch a data-quality violation trigger a CloudWatch alarm. (MLA D4)
  7. (300) Glue + Data Catalog + Athena: Land raw JSON/CSV in S3 → Glue crawler → Data Catalog → query with Athena → add a Glue Data Quality (DQDL) ruleset and watch it fail on bad records on purpose. (DEA D1/D2)
  8. (300) Streaming pipeline: Kinesis Data Firehose from a producer script into S3, vs a Kinesis Data Streams + Lambda consumer for the same data — note the code/ops difference. (DEA D1)
  9. (350) Lake Formation governance: Register your S3 lake location in Lake Formation, grant column-level permissions to a second IAM principal, confirm via Athena that the restriction holds. (DEA D4)
  10. (400 — capstone, HPC territory): If quota allows, spin up a minimal SageMaker HyperPod cluster and run a small multi-node distributed training job — just to see cluster lifecycle, node health checks, and checkpoint/resume behavior firsthand. Rare hands-on experience most exam-takers skip; a genuine resume differentiator. (MLA D2/D3, 2026-relevant)
Study cadence: given your ADHD/execution profile, pair every numbered concept block above with its matching exercise in the same sitting — reading without building won't stick. Don't try to "finish the whole guide" in one sprint; one block, one exercise, close the loop, move on.
